---
title: "Flows in the repo"
description: "Add a flow to the repo, and CI records it again on every merge, committing only when the picture changed."
---

A demo video goes stale when the app changes. Add its flow to the repo, and
CI records it again after each merge and delivers what changed.

## Add a flow

In the repo, with a flow your agent recorded:

```bash
npx demoman add "Add a task" --to docs/add-task.mp4
```

This writes `.demoman/flows/<name>.json`, the flow's recipe: everything a new video needs,
exports its current video to each `--to` path, and writes what those files
show to `.demoman/receipts/<name>.json`, which a refresh compares against.
Commit all three. `--gif` adds a GIF.
A repo whose flows an older Demoman kept in the old folder is still read, and
each recipe moves to `.demoman/flows/` the next time it is added.

The flow's id is in the file, so every machine that clones the repo shares it.
If your own library already holds a different flow with that name, a run
into the repo's flow refuses with `repoFlowNameTaken` and names
`demoman join-flow <from> <into>`, which moves that flow's videos into the
repo's one. Two recipes naming one flow refuse with `duplicateFlow`; a recipe
that will not read refuses with `repoFlowUnreadable`.

Add refuses, writing nothing, a flow whose current video has Studio
edits a new video does not carry (a mask, a trim, a cut, a split, a hold, a
gap, a placed zoom), typed text the video never read, or a site you
signed in to by hand with `signin` rather than as a demo account. The
refusal names which. Record it again without them.

When your agent later runs a script into a flow in the repo, its recipe
follows the script.

## Refresh

```bash
npx demoman refresh
```

Records every flow in the repo again, with no agent. It prints a line per flow:

| Line | Meaning |
| --- | --- |
| `<name>: changed: <what changed>` | The picture changed: how much, and when in the video. The files are overwritten |
| `<name>: added: <which file>` | It looks the same, and an output that was not there yet is written |
| `<name>: uncompared: nothing to compare against; delivered as new` | No earlier video to compare with (no receipt, or no committed file). The files are written |
| `<name>: unchanged: <how much changed>` | It looks the same. The files are left as they are |
| `<name>: failed: <why>` | The run was not clean. The committed files stay, and the command exits 1 |

Refresh compares the screen before each step, and the final screen when the
video rests at the end, in the video it judges: the first MP4 that is not
9:16, else the first file that is not 9:16, else the first MP4. Where the receipt
recorded a still screen, the new video is read at the same step. If the
picture changed, every file of the video is replaced, with its receipt in
`.demoman/receipts/`; the recipe itself is never rewritten. Videos are
not compared byte for byte, so an unchanged app makes no commit. On a
compared screen, a change as small as one digit of body text is seen, and so is a colour change alone: grey text a few
shades lighter, a button turned another colour of the same lightness. Five
gaps are accepted:

- A change seen only in motion or mid-scroll, or something that appears and
  goes within one step, is not seen. It is seen once it shows on a screen
  that is compared.
- A change too small to tell from the video's own compression is not seen:
  a single character in very light text, or a slight shade change over a
  small area, such as a thin border or a small icon.
- An animation always in view, such as a spinner, a clock or a carousel, can
  read as changed on some refreshes: it shows a different frame on a compared
  screen ([#10](https://github.com/demoman-io/demoman/issues/10)).
- A slower app that tips the camera to pull back, where it held before (or
  the reverse), reads as changed. The camera decides from the gap between two
  clicks, and a gap near that line can fall either side of it.
- A flow added on macOS is recorded again on Linux by the first refresh in CI.
  Linux's fonts differ, so that refresh replaces it once. After that, refresh
  in CI only: a refresh on a Mac and one in CI replace each other's files.

A flow with no recorded screens is not refreshed. Its line says to run
`demoman add` for it again.

## Commit no video

```bash
npx demoman add "Add a task" --to add-task.mp4 --deliver files
npx demoman refresh --out-dir demoman-out
```

With `--deliver files`, add writes only the recipe in `.demoman/flows/`, and a
`--to` path is a plain file name. Refresh writes the video and its receipt (neither for a video that came back
`unchanged`) and `demoman-refresh.json`, which lists what each flow made, into
`--out-dir`;
nothing is committed. Upload the folder with your own step, such as
`aws s3 sync demoman-out s3://bucket/`, or
`aws s3 sync demoman-out s3://bucket/ --endpoint-url $R2_ENDPOINT` for R2.
To compare with what was delivered before, give `--previous` a copy of
everything earlier runs delivered, kept whole, such as your bucket synced back
down: an `unchanged` or `added` run writes no receipt into `--out-dir`, so one
earlier run's folder alone is not enough. `--previous` may be the `--out-dir`
itself: refresh compares in place and replaces only what changed, so the
folder stays whole for the next run. With none, every video reads
`uncompared`. A `files` flow refreshed without
`--out-dir` fails, and the others still refresh.

## Run it in CI

```bash
npx demoman setup --ci
```

Setup shows one plan and asks once. It checks the setup from a clean
checkout first, so the plan carries the result; nothing is written to your
checkout, branch or default branch. Then, on your confirmation, it sets the
secrets, turns on the Actions setting, opens a pull request titled "Set up
Demoman" from `demoman/setup`, and watches its first run.

The plan lists:

- the trigger: after a successful deployment, when a release is published,
  once a day, or on each merge. The default is deployment if the repo has
  a successful deployment that names a URL (a production environment first,
  never a preview one), else release if it publishes releases, else daily; push
  is never the default. A trigger the repo has no record of is not offered,
  nor an environment whose name has characters other than letters, digits,
  spaces, `_`, `.` and `-`.
  Push shows its measured cost per merge, or "not measured" with why when
  the check was skipped.
- the route: `pr` (the default) or `main`.
- the files: `.github/workflows/demoman.yml`, `.demoman/app.json` unless
  committed as is, and each repo flow not yet on the default branch. A flow
  goes in with its receipt and exports only when the local video matches the
  script being committed; otherwise the script goes in alone, the plan says
  so, and the first run delivers it as new.
- the secrets, each set, kept or replaced, by name only.
- the Actions setting, when the route is `pr`.

| Flag | |
| --- | --- |
| `--trigger <environment>` | After each successful deployment to that environment; records the deployed app, and the self-check records its newest successful deployment |
| `--trigger release` | When a release is published, at its tag |
| `--trigger daily` | Once a day. A day with nothing new stops before Chromium and the app (`demoman refresh --check --since`) |
| `--trigger push` | On each push to the default branch; records every repo flow each time |
| `--route pr\|main` | Open a pull request with the changed files, or commit them to the branch. Deployment and release cannot use `main` |
| `--artifact` | Keep every `files` flow's video and receipt in the `demoman-videos` artifact, compared against the last run's |
| `--yes` | Confirm the plan with its defaults. With no terminal and no `--yes`, nothing is written and the missing flags are named |
| `--env-file <path>` | Read secret values from this file |
| `--replace-secret <NAME>` | Replace a secret GitHub already has; kept otherwise |

A secret's value goes to GitHub on stdin, never in a command line, a log or
an answer.

### `.demoman/app.json`

The one committed record of how the app starts. Setup proposes it from the
repo, naming where each answer came from, and asks about any it cannot find.
The detector reads, in order, the first that answers: the Playwright config's
`webServer`, a CI workflow, `copilot-setup-steps.yml`, `package.json`.
It never reads `.env`.

| Field | Meaning |
| --- | --- |
| `appVersion` | `1` |
| `install` | Commands run before start, in order |
| `start` | The command that starts the app |
| `url` | Where the app answers. Ready is a 2xx, 3xx, or 400 to 403 |
| `timeoutSeconds` | How long to wait for `url`; default 120 |
| `env` | Environment for the app. Committed, so it refuses a value that looks like a secret |
| `secrets` | Names of secrets the app needs, set on GitHub. Never values |
| `services` | Each service by name: `image`, `ports`, `env`, `options` |

`refresh` starts the app from this file. With `--base-url` it ignores the file
and records the app at that address. It refuses with `appOriginMismatch`,
naming the flows, when a flow records at a different origin than `url`. Off CI it uses an app already
answering at `url`, and otherwise runs `start`. It never starts services: when
the app does not answer and the file declares services, the refusal names
each with its port, to start them yourself. In CI it always starts its own,
and the workflow gives the job the services, corepack (pnpm, yarn) and bun
when the commands use it.

If a workflow of yours already starts the app before `demoman refresh` (a
"Start your app" step, or `wait-on`), delete that step: refresh now starts
the app from this file, and both would take the same port.

### The self-check

The workflow also runs on pull requests that change `demoman.yml` or
`.demoman/**`, as a `check` job that records every flow and commits nothing.
It is the first run of the setup pull request. A pull request from a fork gets
no secrets: the job fails with a message saying so, rather than on a sign-in.

### Stops

Setup says what failed and the next action, and writes nothing outward until
the confirmation. Reasons it names:

| Reason | Meaning |
| --- | --- |
| `ghMissing`, `ghSignedOut`, `notGitHub`, `githubUnreadable` | `gh` is not installed or signed in, the repo is not on github.com, or GitHub could not be read |
| `alreadySetUp` | The workflow is already on the default branch |
| `setupPrOpen`, `setupBranchExists` | A setup pull request is open, or `demoman/setup` is on origin without one |
| `noRepoFlows`, `flowUnreadable` | No repo flow to refresh, or a recipe will not read |
| `noRelease`, `noDeployment` | The chosen trigger has nothing on record |
| `routeRefused` | A trigger and route that cannot go together |
| `workflowRefused` | The workflow cannot be written from these names or values; the detail says which. A secret name needs renaming (in `app.json`'s `secrets` or the account), an environment name or `${{` in a service value means writing that part of the workflow by hand, and a branch name a workflow does not accept needs the branch renamed |
| `appUnknown`, `appHoles`, `appInvalid` | No app found, a field still unknown, or `app.json` is invalid |
| `appOriginMismatch` | A flow records at another origin than `app.json`'s `url`; the detail names each flow and origin |
| `secretsUnknown` | A flow's recipe is unreadable, or no sign-in account can be chosen for its site |
| `secretMissing`, `secretTooShort`, `secretsUnreadable`, `envFileUnreadable` | A secret has no value, an account's value is shorter than 8 characters, GitHub's list of secrets could not be read, or the env file could not |
| `setupUnreadable` | A read or git command failed while planning; nothing was written |
| `filesUnreadable` | A file to commit could not be read; nothing was done |
| `checkoutFailed` | The clean checkout could not be made (no commit, git failing, or a file path outside the repo) |
| `appPortTaken` | Something already answers at `url`; the check will not record it as the app |
| `appInstallFailed`, `appStartExited`, `appNeverAnswered`, `appServiceFailed`, `appDockerMissing` | The check could not install or start the app or its services; the output's last lines come with it |
| `refreshFailed` | The check's refresh failed on a flow |
| `checkStopped` | Ctrl-C ended the check; its worktree is removed and nothing was written |
| `secretRefused` | GitHub refused a secret; the answer names which were set and kept, and no pull request is opened |
| `actionsRefused`, `actionsUnknown` | The Actions setting was refused or could not be read; no pull request is opened |
| `prFailed` | The pull request could not be opened; secrets already set stay |

The watch ends passed, failed, cancelled, or unknown. Unknown means GitHub could
not be read or the run was still going after 30 minutes: never failed, never
passed. After three failed runs on `demoman/setup` it hands back.

Caveats:

- A release published with `GITHUB_TOKEN` starts no workflow, so a release
  trigger fires only for one published by a person or another token.
- GitHub turns a scheduled workflow off after 60 days without activity on a
  public repo; enable it again under Actions.

Your agent does the same with the MCP `add` and `ci` tools. `ci` returns the
plan first and acts only when called with `confirmed: true` after you agree;
it never asks for a secret, and gives you the command to run instead.

### The pull request route

Turn on **Allow GitHub Actions to create and approve pull requests** under
Settings → Actions → General. While it is off, refresh pushes the branch,
opens no pull request, says so, and exits 1.

Refresh force-pushes `demoman/refresh` and opens one pull request titled
"Refresh demo videos", or updates the open one. The description lists each
updated video and its files, and any flow that failed. A workflow token
cannot attach a video, so open the files under "Files changed" to play
them. Commits that were on `demoman/refresh` before the run are replaced,
and the description says so.

### The main route

One "Refresh demo videos" commit on the checked-out branch, pushed. Nothing
is reviewed first.

### No loop

The bot's commit carries `[skip demoman]`, the refresh pull request's
merge commit names `demoman/refresh`, and its squash merge is titled
"Refresh demo videos (#N)". The workflow reads the triggering commit's
message and does nothing when it finds any of them. A rebase merge keeps
the bot's commit message. If you rename the pull request before squashing
it, one more refresh runs; it replaces only a video whose picture changed.

When no video changed, nothing is committed. On the pull request
route, when every flow in the repo was recorded and came back unchanged, an open
refresh pull request is then closed with a comment: its videos are out of
date. When a video failed, or only named videos were refreshed, the pull
request stays open.
